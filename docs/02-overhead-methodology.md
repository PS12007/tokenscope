# 02 — What it costs: measured, not assumed

The README makes two claims. This document is the evidence for both, including
the parts that are not yet settled.

| Claim | Status |
|---|---|
| Zero overhead when compiled out | **Established**, structurally |
| Under 2% when enabled | **Established for every level.** Level 3, the full per-node timeline, measures +0.67% [+0.12, +1.67]. |

---

## 1. Test system

| | |
|---|---|
| CPU | x86-64, 8 threads used |
| OS | Windows 11 (10.0.26200) |
| Compiler | MSVC 19.44.35228, `/O2`, Release |
| Build | `BUILD_SHARED_LIBS=OFF`, AVX2 + FMA + F16C CPU variant |
| llama.cpp | `4d91760` |
| Clock | `std::chrono::steady_clock` (QPC) |

Model: a 24-layer, `n_embd=768`, 12-head / 4-KV-head, `n_ff=3072`, F32
synthetic model (840 MiB, 220 M parameters), generated by
[`tools/make_tiny_model.py`](../tools/make_tiny_model.py).

**Why a synthetic model, and what that costs.** Random weights are exactly as
good as real ones for measuring instrumentation overhead: the profiler's cost
depends on the *shape* of the computation — layer count, node count, thread
count, tokens generated — and not at all on the values in the tensors. It runs
the same matmuls with the same memory traffic. What a synthetic model cannot
support is any claim about how fast a *particular real model* is, or where time
goes in one; those numbers belong in [`FINDINGS.md`](FINDINGS.md) and are
measured against real checkpoints.

The one caveat worth stating: F32 weights mean this run is more
bandwidth-bound than a Q4_K_M run of the same architecture would be, which if
anything makes the instrumentation's relative cost *smaller* than it would be
on a quantized model. Quantized comparisons are pending.

## 2. Claim 1 — zero overhead when compiled out

A statistical test cannot prove the absence of an effect, so this one is not
tested statistically. It is verified against the symbol table and the object
file, where "nothing is there" is a fact rather than an inference.

Building the standalone library both ways:

```
build-off/tokenscope.lib        864 bytes    0 tokenscope symbols
build-on/tokenscope.lib     992,690 bytes   68 exported symbols
```

```
$ dumpbin /symbols build-off/tokenscope.lib | grep -c "ts_"
0
```

The 864-byte archive is an empty one: with `TOKENSCOPE_ENABLED` undefined,
`tokenscope.cpp` is a single `#ifdef` around the entire file, and every macro in
`tokenscope.h` expands to `do {} while (0)`. There is no function to call, no
flag to test, and no storage to reserve.

That is the whole argument, and it is the reason the design puts the disable
switch at the preprocessor rather than at a runtime branch.

## 3. Claim 2 — under 2% when enabled

### The three configurations

Quoting a single before/after number is how profilers end up reporting a figure
that is not about the profiler at all. Three arms:

| Arm | Build | Runtime | Measures |
|---|---|---|---|
| **A** | `GGML_TOKENSCOPE=OFF` | — | true baseline |
| **B** | `ON` | `TOKENSCOPE_LEVEL=0` | cost of the residual enable-flag check |
| **C1** | `ON` | `TOKENSCOPE_LEVEL=1` | host scopes only |
| **C2** | `ON` | `TOKENSCOPE_LEVEL=2` | + per-node aggregates, constant memory |
| **C3** | `ON` | `TOKENSCOPE_LEVEL=3` | + every node event on every thread |

**A vs B** is the honest test of "you can ship a build with this compiled in and
turned off." **B vs C** is what a user pays to actually profile.

### Protocol

- 15 repetitions per arm, arms **interleaved** (ABC ABC ABC…), never blocked.
  Thermal drift and background load then hit every arm equally instead of
  landing entirely on whichever arm ran last.
- First repetition of each arm discarded as warm-up.
- **Median and interquartile range**, not mean and standard deviation. A tok/s
  distribution has a hard ceiling and a long slow tail; the mean tracks the tail,
  which is the machine's noise rather than the effect being measured.
- Overhead reported as a **bootstrap 95% confidence interval** over 20,000
  resamples of each arm, so the result is a range and not a point estimate
  pretending to be one.
- The harness refuses to quote a number when the baseline arm's own IQR exceeds
  the effect size under test.

Implementation: [`tools/bench_overhead.py`](../tools/bench_overhead.py).

### Session 1: levels 0 and 1 only

Taken before Tier 2 existed, when level 1 meant a single scope per
`llama_decode` call. Kept because the sessions together make the point about
measurement noise below.

#### decode (tg256, 8 threads, 15 reps)

```
  arm                       median tok/s     IQR   overhead vs A
  --------------------------------------------------------------------
  A: compiled out                  42.23    0.4%                  -
  B: in, level 0                   42.19    0.8%    +0.11%  [-0.25, +0.76]
  C1: active level 1               42.25    0.7%    -0.04%  [-0.48, +0.45]

  baseline IQR is 0.42% of median.
```

#### prefill (pp512, 8 threads, 15 reps)

```
  arm                       median tok/s     IQR   overhead vs A
  --------------------------------------------------------------------
  A: compiled out                 682.96    1.1%                  -
  B: in, level 0                  677.96    1.5%    +0.74%  [-0.27, +1.80]
  C1: active level 1              680.33    1.3%    +0.39%  [-0.52, +1.27]

  baseline IQR is 1.11% of median.
```

### Reading this correctly

Every confidence interval contains zero. The correct statement is therefore
**not** "overhead is 0.11%". It is:

> At level 1, tokenscope's overhead is not distinguishable from zero on this
> system, with a resolution of roughly ±0.5% on decode and ±1.3% on prefill.

The negative point estimate on decode (`-0.04%`) is not the profiler making
inference faster. It is noise, and reporting it as a speedup would be exactly
the kind of dishonesty this methodology exists to prevent.

### Session 2: re-measured after full Tier 1 instrumentation

The numbers above were taken when level 1 meant **one** scope per `llama_decode`
call. Level 1 now records **eleven**: `batch-init`, `sched-reserve`,
`kv.update`, `kv.slot-search`, `output-reserve`, `ubatch`, `graph-build`,
`graph-alloc`, `set-inputs`, `graph-compute`, `logits-readback`.

Re-run, 21 repetitions per arm:

```
decode (tg256)
  arm                       median tok/s     IQR   overhead vs A
  --------------------------------------------------------------------
  A: compiled out                  42.49    2.3%                  -
  B: in, level 0                   42.53    1.3%    -0.11%  [-1.31, +0.89]
  C1: active level 1               42.37    1.1%    +0.26%  [-0.93, +1.27]

  baseline IQR is 2.26% of median.
  NOTE: that is wider than the 2% budget being tested.

prefill (pp512)
  A: compiled out                 681.60    1.5%                  -
  B: in, level 0                  681.25    1.3%    +0.05%  [-0.88, +0.88]
  C1: active level 1              683.54    1.3%    -0.28%  [-1.29, +0.55]

  baseline IQR is 1.48% of median.
```

Eleven scopes instead of one, and the result is still indistinguishable from
zero — bounded by ±1.3% rather than ±0.5%, because **this session's machine was
noisier**, not because the instrumentation got more expensive. The decode arm's
baseline IQR moved from 0.42% to 2.26% between sessions on identical binaries
and an identical workload.

That drift is worth stating loudly, because it is the thing most likely to make
someone else's reproduction disagree with this document:

> **The noise floor of the measuring machine varies by 5× between sessions.**
> Any overhead figure quoted without its baseline IQR alongside it is not a
> measurement, it is a number.

This is exactly why the harness prints the baseline IQR next to every result and
refuses to quote an overhead figure when the noise exceeds the effect. On the
run above it declined for decode and accepted for prefill, which is the correct
behaviour in both cases.

The defensible combined statement across both sessions:

> At level 1, with eleven scopes per token, tokenscope's overhead is below the
> measurement floor on every run taken so far. The tightest bound obtained is
> ±0.5%; the loosest is ±1.3%. No run has produced a point estimate outside
> ±0.3%.

### Session 3: levels 2 and 3, and the first measurable overhead

Level 3 records **every graph node event on every worker thread** — roughly
1,400 records per token per thread, ~2.9 million records over a `tg256` run.
This is the arm the whole design was worried about.

15 repetitions, 5 arms, interleaved:

```
decode (tg256, 8 threads)
  arm                       median tok/s     IQR   overhead vs A
  --------------------------------------------------------------------
  A: compiled out                  42.41    0.7%                  -
  B: in, level 0                   42.28    1.6%    +0.31%  [-1.13, +0.79]
  C1: active level 1               42.26    2.3%    +0.36%  [-0.61, +1.80]
  C2: active level 2               42.12    1.7%    +0.69%  [-0.01, +1.86]
  C3: active level 3               42.13    1.1%    +0.67%  [+0.12, +1.67]

  baseline IQR is 0.70% of median.
```

**Level 3 is the first arm whose confidence interval excludes zero.** After five
measurement sessions in which every result was "indistinguishable from zero",
this one is an actual effect:

> **Level 3 overhead is +0.67%, 95% CI [+0.12, +1.67].**

Level 2 sits at +0.69% [-0.01, +1.86] — the interval grazes zero, so it is
suggestive rather than established.

Both are inside the 2% budget. The upper bound of the level 3 interval (+1.67%)
is inside it too, which matters: the claim survives the pessimistic end of the
measurement, not just the point estimate.

### Verifying the level 3 number is not an artifact of dropped records

A profiler that fills its buffer and stops recording gets cheaper. If the
budget had been exhausted partway through the `tg256` run, the measured
overhead would be for a partial trace and the number would be worthless.

Checked directly, on the exact benchmark workload:

```
tokenscope: wrote full3.json (228,723,230 bytes, 259 tokens, 8 threads, 0 dropped)
```

**Zero dropped.** The full run was recorded, so +0.67% is the cost of recording
all of it.

That 229 MB is itself the practical constraint on level 3: it is close to the
256 MB default budget, and a longer run would hit it. That is what
`TOKENSCOPE_TOKENS=340-345` is for, and it is why level 2's constant-memory
aggregate mode exists.

### Why the cost is this low, and why that was not obvious

The naive model in docs/01 predicted ~0.1% and explicitly warned it might not
hold, for two reasons that the model does not capture:

- **cache pollution** — records evicting weights in a bandwidth-bound workload;
- **the barrier** — per-thread jitter becoming whole-graph latency, since the
  graph waits for the slowest thread at each of ~700 barriers per token.

Measured at +0.67% against a ~0.1% naive prediction, both effects are real —
the cost is roughly 6× the arithmetic — and both are small enough in absolute
terms to stay well inside budget. The mitigations appear to have worked:
collapsing four clock reads per node into two, keeping records at 24 bytes, and
pre-touching chunks so no allocation happens inside a graph.

That is a satisfying place to land, but the honest framing is that the design
predicted the *right risks* and got the *magnitude* wrong by 6×. The naive cost
model is not a substitute for the measurement, which is the entire argument of
this document.

### Why the order of these sessions mattered

Session 1 measured a mechanism with **one** scope in it. That looked like a
weak result at the time — and it was the point.

The plan ([`01`](01-design-scope-timing.md) section 11) was to measure the
mechanism before expanding scope, so that if a number ever came back too high
there would be exactly one place it could be coming from. Session 1 established
two things that only look useful in hindsight:

- the fixed cost of the mechanism — TLS access, buffer reserve, two clock reads,
  a 24-byte store — is below the system's noise floor;
- the harness can resolve 0.4% at all, which is the precondition for measuring
  anything smaller than 2%.

Without that, session 3's `+0.67% [+0.12, +1.67]` would be a number with
sixteen instrumentation sites behind it and no way to attribute it. With it, the
progression 0.31% → 0.36% → 0.69% → 0.67% across arms B, C1, C2, C3 reads as a
cost curve rather than a single opaque figure.

### Remaining gaps in the overhead claim

- **Linux/GCC untested.** Everything here is MSVC on Windows. The TLS
  characteristics that shaped the design are Windows-specific, and GCC's
  `__thread` is cheaper, so the expectation is that Linux is no worse — but
  expectation is not measurement.
- **Shared-library builds untested.** All measurements are
  `BUILD_SHARED_LIBS=OFF`. The `__declspec(dllimport)` path adds an indirection
  per global read on Windows.
- **Thread-count sweep not done.** docs/01 argued that barrier effects make
  overhead a `max()` across threads rather than a mean, which predicts that
  overhead grows with thread count. Only 8 threads has been measured. A 1 / 4 /
  8 / oversubscribed sweep is the test of that prediction.
- **Quantized models untested**, as noted in section 1.

### The isolated per-scope cost

Independently of the end-to-end benchmark, the self-test measures the scope
mechanism directly, in a tight loop:

```
$ ts_selftest
  measured: 52.8 ns per scope (2 clock reads + 1 store)
```

That decomposes as roughly 26 ns per `steady_clock::now()` plus a few ns of
bookkeeping — which is the number that justifies the clock-collapsing design in
the node loop. When a node emits both a work scope and a wait scope, sharing one
timestamp between them removes an entire clock read, and the clock read is
~90% of the cost. Optimizing the store would have been the obvious move and the
wrong one.

Projecting forward with that number: 500 nodes/token × 2 events × ~26 ns is
~26 µs of instrumentation per token per thread, against a measured 23.6 ms
token. That is ~0.1% *if the cost model holds*. The cost model is precisely
what sections 8.1 and 8.2 of docs/01 argue may not hold, so this projection is
a hypothesis to be tested, not a result.

## 4. Reproducing this

```bash
python scripts/bootstrap.py --dest ../llama.cpp

cmake -S ../llama.cpp -B ../llama.cpp/build-ts-off -DCMAKE_BUILD_TYPE=Release \
      -DBUILD_SHARED_LIBS=OFF -DGGML_TOKENSCOPE=OFF
cmake --build ../llama.cpp/build-ts-off --target llama-bench

cmake -S ../llama.cpp -B ../llama.cpp/build-ts-on  -DCMAKE_BUILD_TYPE=Release \
      -DBUILD_SHARED_LIBS=OFF -DGGML_TOKENSCOPE=ON
cmake --build ../llama.cpp/build-ts-on --target llama-bench

python tools/make_tiny_model.py --llama-cpp ../llama.cpp -o models/mid.gguf \
       --layers 24 --embd 768 --heads 12 --heads-kv 4 --vocab 8192

python tools/bench_overhead.py --model models/mid.gguf \
       --bin-off ../llama.cpp/build-ts-off/bin \
       --bin-on  ../llama.cpp/build-ts-on/bin \
       -n 15 -t 8 --n-gen 256 --n-prompt 512 --levels 1
```

Expect roughly 6 minutes. If your baseline IQR comes back above 2%, the harness
will tell you so and decline to quote an overhead figure; close background work
and rerun rather than believing the number anyway.

## 5. A note on what the first run already showed

The very first trace, on an 8-layer model, reported **1405 tok/s** for decode
while `llama-bench` reported **1452 tok/s** for the same run. A 3% gap.

That gap is not an error in either number. `llama-bench`'s figure covers its own
generation loop; tokenscope's slice covers `llama_context::decode` from entry to
exit, and `llama_synchronize()` is called *after* `decode()` returns
(`tools/llama-bench/llama-bench.cpp:2215`). The difference is real work that
happens outside the boundary we drew.

On the 24-layer model the same comparison is 42.3 vs 42.36 tok/s — 0.1%, because
the synchronize is a fixed cost and the token got 33× longer.

This is worth recording for two reasons. It is a small first confirmation that
the instrumentation is measuring what it claims to. And it is a live example of
the thing doc 00 section 1 complains about: **where you draw the boundary
changes the number**, and a profiler that does not tell you where its boundary
is has not really told you anything.
